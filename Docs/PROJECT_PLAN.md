# Project Plan: An Open-Source Successor to NoLimits 2

*Working title: TrackUnlimited. Prepared August 2, 2026.*

## 1. Vision

NoLimits 2 has been the gold standard for precision roller coaster simulation since 2014 — accurate enough that real manufacturers like Vekoma, Intamin, Maurer Söhne, and Gerstlauer use it to prototype designs, and enthusiast-friendly enough to have sustained an active Steam Workshop community for over a decade. But it is a decade-old engine wearing a decade-old interface, built by a three-person team (Tom Zeliff, Ole Lange, Kevin Stone) that has slowed to roughly one meaningful update every few years. The community's own words on it: "new coaster types have dried up," the editor is "pages and pages of tools to cycle through," and forums that once buzzed are largely quiet now.

The goal of this project is a free, open-source, Unreal Engine 5–built coaster simulator that matches NoLimits 2's engineering rigor — real physics, accurate G-forces, CAD-precision track editing — while presenting it through a modern, approachable interface and next-generation visuals. This is the **hybrid positioning**: a pro-grade simulation core with a friendly on-ramp, so it's credible to the enthusiasts and professionals who rely on NL2 today, but not intimidating to a new player who just wants to build a fun coaster and watch it run.

Scope for now: **PC only, flatscreen**, solo-developer-led, free and open source. VR is a natural stretch goal later (NL2's VR support is one of its most-loved features), but it adds real engineering cost and is explicitly deferred rather than baked into the initial architecture as a hard requirement — though the render/camera pipeline should not actively foreclose it.

One more thing worth stating up front because it emerged directly from the developer's own background: neither NL2 nor Planet Coaster meaningfully simulates the *operator's* side of running a coaster — block signaling, dispatch permissives, and the control-room hardware (VFDs, indicator panels) that real ride operators actually work with. Building that as a real, generated-from-the-track-data system (not a cosmetic prop) is a genuine, currently-unclaimed differentiator, not just a nice-to-have.

## 2. Market Context

**NoLimits 2** ($39.99, ~96% positive on Steam) remains the reference tool: 40+ coaster styles, a CAD-style editor, VR ride-throughs, Steam Workshop, and professional adoption. Its weaknesses are development pace (its most recent DLC, the Vekoma MK1101 add-on, shipped in June 2024 — four years after the prior major update in January 2020), UI complexity, and the lack of any in-editor scenery/landscaping tools (users have to export wireframes to external 3D software to dress up a park).

**Planet Coaster / Planet Coaster 2** occupies the opposite end: gorgeous, accessible park-building with real-time coaster construction, but it is not built for engineering-grade physics or precise G-force/heartline analysis — it's a management/building game first, a simulator second.

The gap this project targets: nobody currently offers NL2's engineering fidelity with Planet Coaster's approachability and modern engine visuals. That gap is real and has stayed open for years, which is exactly why NL2 — despite its age — hasn't been displaced.

Two pieces of existing prior art are worth knowing about before writing a line of code. **Coaster Forge** (Dualstate Games, distributed on Fab) is an existing Unreal Engine marketplace asset that already does procedural coaster generation from spline parameters — auto-generated rail geometry, ground-anchored supports, rail "zones" (station/brake/boost/lift) with physics-driven train speed behavior, and instanced-mesh rendering for performance. It's worth evaluating directly as a licensing/reference option rather than reinventing procedural track meshing from zero — even if it's ultimately not used verbatim, its zone-based approach to speed control is a solid design pattern to borrow. Several open Unreal Engine forum threads ("Roller Coaster Like Physics Along a Spline?", the old UE4 Rollercoaster Plugin wiki page) also cover spline-follow physics approaches worth reviewing early.

## 3. Product Pillars

The plan organizes around five pillars, roughly in priority order for a solo developer:

1. **Track editing precision.** Curvature-continuous (not just position-continuous) spline editing, so track is smooth the way NL2's is — no visible kinks, correct banking, accurate transition curves. This is the single feature that most defines whether the tool is credible to the NL2 audience.
2. **Physics fidelity.** Energy-conserving motion along the track (gravity, friction, drag, block-brake behavior), a live G-force readout, and a heartline-relative camera for ride-throughs — the same "trust the numbers" bar NL2 set for professional use.
3. **Approachable UX.** Real-time visual feedback (G-force graphs overlaid on the track, color-coded speed/force heatmaps), sane defaults, and a UI that doesn't require a manual to find the tool you want — this is the pillar Planet Coaster proves is possible and NL2 has never really delivered.
4. **Modern presentation.** UE5's Lumen/Nanite for park visuals, weather and time-of-day, and a rendering pipeline good enough that ride-through videos are share-worthy (NL2's video export feature was popular for exactly this reason).
5. **Ride control and signaling.** A real block-signaling system (occupancy + safety-overlap buffer, not just "train present/absent") driving an automatic dispatch system with a manual-override mode, and a control panel — generated directly from each coaster's own block/segment data, not hand-authored — that visually shows the actual causal chain a real ride runs on: a sensor trips, that trips an indicator on the panel, the panel/logic layer commands an actuator (a VFD-driven motor, a brake), and the actuator responds. This is the pillar with no real precedent in either NL2 or Planet Coaster, and it's the one area where the developer's own prior work (spline train sims with automatic control and signaling) is most directly applicable.

## 4. Scope: MVP vs. Full Vision

Solo-developer, free/open-source projects die most often from scope creep, not from lack of ambition. The plan below is deliberately staged so there is a genuinely shippable, demonstrable milestone at the end of every phase — each one is something you could post a devlog/video about, which matters for attracting open-source contributors later.

**MVP definition:** a single coaster, on a flat plot, buildable with a smooth curvature-continuous spline editor, physically simulated (gravity/friction/drag), with a working ride-through camera and a live G-force readout. No scenery system, no multi-coaster parks, no workshop sharing yet. This alone is already a meaningful, demoable product — it's roughly "NL2's original 2001 scope," which is itself worth remembering: NL1 shipped as a single-purpose, tightly-scoped tool and grew from there.

**Full vision (post-MVP):** park-level scenery placement and terrain sculpting, multiple coasters per park, a support-structure auto-generator, custom track styles (wood/steel/launch/inverted variants), a generated ride-control panel with automatic/manual dispatch, a save-file/workshop-equivalent sharing pipeline, and eventually VR ride-throughs.

## 5. Technical Architecture

**Engine and language.** Unreal Engine 5, C++ for the simulation/physics core (performance- and precision-critical), Blueprints for editor tooling, UI, and rapid iteration on non-critical systems. This split matters for a solo dev: C++ where correctness and speed are non-negotiable, Blueprint where iteration speed matters more.

**Track representation.** The core data structure is not a raw Unreal `SplineComponent` used naively — position-only splines produce visible curvature discontinuities exactly where NL2's track feels smooth. The track is represented as a sequence of curvature-continuous segments, each defined as a **curvature profile over arc length**: curvature varies linearly across a segment, so a straight is `k = 0`, a constant-radius curve is `k = const`, and a clothoid is `k` linear. Geometry comes from integrating a moving orthonormal frame along that profile. The reason for this form is that C² continuity becomes a property of the data rather than something fitted after the fact — if curvature is continuous across a joint, the geometry is, with nothing to solve — and transition curves become the native case instead of special handling. *(This supersedes the cubic Hermite / B-spline formulation originally specified here; the change was made after the Phase 0 prototype, and its full rationale lives in `Prototypes/TrackSpline/TrackSpline.h` where it cannot drift from the code. Consequences, including the one real cost — no endpoint targeting, so closing a circuit is an inverse solve — are in `Docs/PHASE0_FINDINGS.md`.)* Transition curves (Euler spirals/clothoids) are the standard real-world technique for banked-curve entry/exit and are what makes physical coaster track — and NL2's simulated track — feel smooth instead of jarring. Roll (banking) should be defined independently along the same curvilinear parameter as position, following NL2's documented "heartline" design approach: bank angle is computed around an offset heartline rather than the rail centerline, which is what keeps the rider's felt-G experience physically sensible through banked turns.

**Physics simulation.** Rather than relying on Unreal's Chaos rigid-body physics for the train itself (which would fight for the precision this project needs), the train's motion along track should be simulated with a 1D energy/force model constrained to the spline: potential/kinetic energy exchange, rolling friction, air drag, and explicit handling of powered segments (lift hills, launches, brakes/block zones). Chaos Physics still has a role for secondary effects — rider ragdoll/camera shake, debris, scenery collision — just not for the core ride simulation. This mirrors how NL2 itself works and how Coaster Forge's "zone" system (station/brake/boost/lift, each with a target speed) approaches it.

**Track editor UX.** Numeric/formula-driven, not direct-manipulation. There is deliberately no click-drag-place viewport interaction for track geometry (the thing Coaster Forge and most Unreal spline tools default to, and explicitly what this project is avoiding — closer to Satisfactory's snap-and-drag than to a real alignment tool). Instead, a track is an ordered list of parametric segments (straight, constant-radius curve, clothoid transition, helix), each defined by typed values or expressions — note that the helix is *not* expressible as a linear curvature profile and needs its own segment type plus either a world-vertical yaw term in the integrator or a non-linear profile shape, per `Docs/PHASE0_FINDINGS.md`; the 3D view and the live speed/G-force/banking graph are read-only previews driven off that data, not the editing surface itself. This is a better fit for version control too — the segment list serializes directly to the diffable save format described below. Undo/redo needs to be built in from day one against this data model (not bolted on later — retrofitting undo into a hand-rolled data model is a common solo-dev trap).

**Signaling and ride control.** This is its own subsystem, built in C++ like the physics core (the developer's prior Blueprint-based signaling system should be treated as a design reference, ported to C++ rather than reused as Blueprint — Blueprint graphs don't carry over into a from-scratch codebase anyway, and this logic is exactly the kind of correctness-critical code that belongs in C++). Each block is a small state machine: `CLEAR → OCCUPIED` (train physically within the block) `→ BUFFER(x)` (train has exited, but the block withholds CLEAR until a configurable time/distance safety overlap elapses, mirroring the real-railway "overlap" concept) `→ CLEAR`. Dispatch permissive logic reads forward through this block list — a station or launch may dispatch only once the next block (and, for high-speed sections, as many blocks ahead as the train's braking distance requires) reports CLEAR. The block list is modelled as a closed **circuit**: lookahead wraps past the last block to the first, and a lookahead spanning the whole circuit is denied because it would include the asking train's own block. That is correct for a circuit and wrong for a shuttle or a transfer spur, which will need an explicit topology when they exist. On top of that sits a dispatch mode, matching how real ride control systems actually run: **automatic**, where the system dispatches as soon as permissives are satisfied, and **manual**, where a human operator decides when to dispatch or hold — but the safety interlocks (permissive logic) apply identically in both modes; manual mode changes who decides the timing, not whether the safety logic can be bypassed.

The control panel itself should be *generated*, not hand-built per coaster: walk the same ordered block/segment list that drives the 3D mesh and physics, and for each block emit an indicator (clear/occupied/buffer-countdown), and for each powered segment (lift chain, tire-drive launch) emit a VFD module (target frequency/speed, actual motor feedback, torque/current, ramp rate). The panel is a second generated view over the same canonical track data as the geometry and physics — one more thing driven parametrically rather than authored by hand, consistent with the track editor's own philosophy. Just as important as the data model is making the causal chain *visible* to the player: when a sensor trips, that should visibly propagate — the sensor indicator lights, the logic layer evaluates it, and the resulting actuator command (a VFD ramping a motor, a brake engaging) should be observable, not just an instantaneous state change. That visibility is most of the pedagogical/differentiating value of this pillar — it's what makes the system feel like a real ride control system instead of an invisible if-statement. Presentation is staged: a 2D generated HMI/panel view first (keeps the system strictly data-driven and cheap to build), with an optional 3D-modeled control booth as a later presentation layer over the same underlying data, not a separate system.

**Procedural mesh generation.** Rail, tie, and support meshes generated from the spline data using instanced static meshes for performance (this is where evaluating Coaster Forge directly, rather than building from scratch, could save months). Support auto-generation (placing and sizing support towers to reach the ground) is a genuinely hard sub-problem and should be treated as its own milestone, not an assumed detail.

**Rendering.** Lumen and Nanite for park environments and lighting; this is one of the cheapest ways for a solo dev to get a visual quality bar competitive with a AAA-backed title like Planet Coaster 2, since Epic is doing the heavy lifting.

**Save format.** A versioned, human-diffable format (JSON or a custom text format) rather than an opaque binary — this matters enormously for an open-source, community-driven project: it enables text diffs in version control, hand-editing, and third-party tooling, all of which NL2's community has historically wanted and often had to work around.

**Sharing/community layer.** Since this is open source and free, there's no Steam Workshop to lean on by default. Plan for a simple community-hosted sharing mechanism (even something as low-tech as a GitHub-based or itch.io-hosted repository of `.parktrack` files early on) rather than deferring community sharing indefinitely — NL2's community strength came directly from Workshop-style sharing, and losing that (as its Exchange platform's death shows) visibly hurt its community.

## 6. Roadmap (Solo-Developer Paced)

| Phase | Goal | Shippable artifact |
|---|---|---|
| 0 — Prototype (4-8 weeks) | Prove the core feel: a hand-authored spline, a cart that follows it with real physics, a basic camera. Evaluate Coaster Forge and other existing UE assets here before committing to build-from-scratch. | A single hardcoded loop you can ride, with correct-feeling G-forces. |
| 1 — Track Editor MVP (2-4 months) | Numeric segment-list editor (typed values/expressions per segment), banking control, undo/redo built in from day one, live G-force graph, circuit closure solver. | Build an arbitrary coaster from scratch in-editor. |
| 2 — Physics & Ride Feel (1-2 months) | Friction/drag tuning, lift hills, launches, block brakes, heartline camera polish. | A ride-through that "feels right" to an NL2 veteran — this is the credibility milestone. |
| 3 — Ride Control System (1-2 months) | Block state machine (occupancy + buffer/overlap), dispatch permissive logic, auto/manual dispatch modes, generated 2D control panel with VFD visualization tied to sensor/actuator events. | You can watch (or run) a coaster dispatch itself safely from a real generated control panel — the second credibility milestone, and the project's clearest differentiator. |
| 4 — Track Meshing & Supports (1-2 months) | Procedural rail/tie/support generation, at least one visual track style. | A coaster that looks like a real structure, not a spline in space. |
| 5 — Scenery & Park Layer (2-3 months) | Terrain sculpting, static scenery placement, basic landscaping. | A small themed area around the coaster. |
| 6 — Sharing & Open-Source Launch (1 month) | Save/load, export format documentation, public GitHub repo, first public build. | A public 0.1 release + devlog/announcement. |
| 7 — Community Growth (ongoing) | Onboarding docs for contributors, issue triage, expand coaster styles based on community demand. | Growing contributor base. |
| Stretch — VR, 3D control booth | Revisit once the flatscreen core is solid; camera/interaction rework required for VR, art pass required for a physical booth. | VR ride-through mode; walk-in 3D control room. |

Phases 0–3 are the highest-risk, highest-value work and deserve the most patience — everything after Phase 3 is comparatively conventional game-dev work, but a coaster sim that doesn't *feel* physically right, or doesn't dispatch safely, is worthless regardless of how good the scenery tools are.

## 7. Solo-Dev Execution Strategy

Three things matter more than usual for a solo, free, open-source project of this ambition, plus one advantage specific to this project: the ride-control/signaling pillar (section 3, pillar 5) is not a cold start — it's a from-scratch C++ rebuild of a block-occupancy-plus-buffer system the developer has already designed, shipped, and validated once in Blueprint. That's real, banked risk reduction on what would otherwise be the newest and least-proven part of the plan; it deserves the confidence that comes with "I've built this before," not the caution owed to the rest of the untested architecture. First, **build in public early** — devlogs or short clips at the end of each phase (especially Phase 0-2) are how open-source contributors and an eventual community get recruited; NL2's own community shows how much a coaster-sim audience wants to engage with development progress. Second, **leverage existing assets aggressively** rather than building everything from scratch — Coaster Forge and similar marketplace/open-source spline-physics work exist specifically because this problem has been solved partially before; evaluating and licensing/adapting rather than reinventing is the single biggest lever available to compress a multi-year solo effort. Third, **protect Phase 0-2 from scope creep** — it will be tempting to start on scenery or park layout because it's more visually rewarding than tuning friction coefficients, but the physics core is the entire reason this project would be credible to the audience that made NL2 successful in the first place.

## 8. Legal and Licensing Notes

A few things worth deciding early rather than retrofitting. Unreal Engine's own source code cannot itself be re-published in a separate public repository — it's available via Epic's GitHub under EULA to linked accounts, but a public open-source release of this project should distribute *your* project code/content (C++ gameplay code, Blueprints, assets) and instruct users to obtain the engine themselves via Epic Games Launcher or their own linked GitHub access, which is exactly how other open-source UE projects operate. Pick an explicit OSS license for the project code (MIT/Apache-2.0 are common permissive choices for game code; GPL is more restrictive but common where you want derivative works to stay open) — this should be decided before the first public commit, not after contributors show up. Finally, avoid using real manufacturer or ride-model trademarks (Vekoma, Intamin, B&M, RMC, etc.) or their exact train/track designs without permission — NL2 has official manufacturer licensing relationships for this; a free open-source project should either use original/generic coaster-style names or pursue its own manufacturer relationships later, not assume fair use.

One more concrete case worth flagging: the developer's prior spline-train prototypes were built on **Train and Rail System** (Polygon Jelly, Unreal Marketplace), a paid asset. That asset is a legitimate design reference — its physics tuning ranges and general "distance-along-spline" runtime pattern are useful to have seen work in practice — but it cannot be shipped, redistributed, or have its code reused in the public open-source repository. The new project's runtime should be built from scratch, informed by but not derived from it.

## 9. Key Risks

| Risk | Why it matters | Mitigation |
|---|---|---|
| Physics/track-editor/signaling complexity is underestimated | This is genuinely hard software (curvature-continuous curve math, energy-based simulation, a correctness-critical block-signaling state machine) — most "coaster sim" side projects stall here | Treat Phase 0-3 as the real project; everything after is comparatively standard. The signaling piece specifically is lower-risk than the rest, since it's a direct evolution of a system the developer has already built and shipped once. |
| Solo-dev burnout / stalled momentum (the exact fate that hit NL2) | A project with no team and no revenue has no external pressure keeping it moving | Public devlogs, small shippable phases, actively recruit contributors starting at Phase 1 |
| Scope creep toward "full park builder" | Planet Coaster's scope is a multi-year AAA-funded effort | MVP is explicitly one-coaster-on-a-flat-plot; park layer is Phase 5, not Phase 1 |
| No monetization means no funding cushion | Free/open-source was the explicit choice here, so this is accepted rather than a flaw, but it does mean no paid contractors, asset purchases, or marketing budget | Rely on marketplace-asset evaluation (e.g., Coaster Forge) instead of custom art/tooling budget where reasonable |
| Legal exposure from manufacturer trademarks/track designs | NL2's manufacturer partnerships exist for a reason | Original naming/generic styles by default; pursue explicit permission before using real manufacturer branding |

## 10. Immediate Next Steps

Before writing production code: spend a short, time-boxed period (a week or two) evaluating Coaster Forge and the other existing Unreal spline-physics prior art hands-on, to decide build-vs-adapt for the procedural meshing layer. In parallel, prototype two things in isolation, outside full engine integration, since both are mathematical/logical cores the rest of the project depends on: the curvature-continuous spline math (even as a standalone script), and the block-occupancy-plus-buffer state machine as a plain C++ class with unit tests, ported directly from the design already proven in the Blueprint prototypes. Only after those are de-risked should Phase 0 (in-engine prototype) begin in earnest.

**Status (2026-08-02):** both original prototype gates are passed — `Prototypes/TrackSpline/` and `Prototypes/BlockSignal/`, results in `Docs/PHASE0_FINDINGS.md`. Three prototypes were added beyond the original plan, each for the same reason: de-risking outside the engine is cheaper than inside. `Prototypes/TrainPhysics/` is the energy-based motion model of Section 5. `Prototypes/NL2Csv/` and `Prototypes/NL2Telemetry/` read NoLimits 2's spline export and live telemetry, so the model can be checked against an independent simulator rather than only against closed forms.

**The in-engine vertical slice is done** — `Source/TrackUnlimited/TUCoasterRide.cpp`. A hand-authored 543.7 m layout builds clean against UE 5.8.1, rides, and reads out speed and G on screen. `Build.cs` includes the prototype headers directly rather than copying them, so the standalone assert suites test exactly the code that ships. That closes the Phase 0 engineering work.

Two "Still unknown" items are also resolved. **The lateral-G sign matches NoLimits 2** — 627/627 samples agree, and the documentation reading that suggested otherwise was wrong, so no negation is needed anywhere. **`RollingResistance` and `DragK` have a first measurement** against NL2's own speed trace; the fitted values are recorded but deliberately not adopted as defaults, because one train on one 233 m layout is a data point rather than a calibration.

**The Coaster Forge evaluation is the last open Phase 0 item**, and it needs a decision rather than more work. Worth noting when making it: this repo is MIT and `CLAUDE.md` constraint 3 bars any paid marketplace asset from committed or shipped code, so the "adapt" half of build-vs-adapt is already foreclosed — the purchase would buy reference reading, not a shortcut. The zone-based speed control this section originally cited as the pattern worth borrowing has meanwhile been arrived at independently and verified against NL2 (`FTrackZone`). What genuinely remains unproven for Phase 4 is technique, mostly support auto-generation, which this plan already flags as its own milestone. A generic track cross-section now exists in `Prototypes/TrackSpline/TrackProfile.h` — gauge, rail and spine dimensions, tie spacing — so meshing has a specification to work against.
